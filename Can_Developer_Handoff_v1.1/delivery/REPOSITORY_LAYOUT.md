# Рекомендуемая структура одного private-репозитория

Начальный коммит — содержимое этого архива. Не загружать параллельно старый v1.0 как активную документацию. Зафиксировать `spec-v1.1`; дальнейшее изменение правил через PR/CHANGELOG.

```text
README.md
DEVELOPER_HANDOFF.md
AGENTS.md
CAN_SPEC_v1.1.md
docs/                 требования и архитектура
contracts/            контракт/проект схемы
reference/            эталон арифметики и тесты
qa/                   проверка пакета и evidence
 design/              UX-референсы, позже утверждённые макеты
 delivery/            план, входные данные, приёмка
 apps/ios/            исполнитель создаст Xcode проект + widget
 services/api/        исполнитель создаст сервер/миграции/интеграционные тесты
 services/worker/     worker (может быть одним backend codebase)
 infra/               исполнитель создаст deploy/backup/monitoring
```

Пустые apps/services не являются реализацией; их нет в пакете как будто уже готового кода. Секреты/реальные данные/бэкапы в репозиторий не добавлять. В организации роль Write подходит для внесения кода; owner остаётся у заказчика [S-10]. Обязательные review/branch protections настраивать с учётом доступного GitHub plan, не считать их включёнными данным ZIP.
