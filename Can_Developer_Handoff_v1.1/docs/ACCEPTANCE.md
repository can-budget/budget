# 09. Приёмка и Definition of Done

Для каждого AC: build/commit/environment, тестовые данные, шаги, ожидаемое, фактическое, доказательство, результат PASS/FAIL/NOT RUN. Все ниже обязательны для соответствующего этапа; «не запускали» не PASS. Две реальные установки — основная проверка UX; 10 участников/гонки также серверными интеграционными тестами на PostgreSQL, не требуется покупать 10 iPhone.

## Доступ и кабинет

**AC-01.** Apple-only вход двух различных пользователей, восстановление на новом устройстве, отмена входа и истёкшая сессия без потери outbox.
**AC-02.** Кабинет одного пользователя полностью работает. Десять равноправных участников; одиннадцатый отклонён без расходования чужого доступа. Creator не имеет скрытого суперправа.
**AC-03.** Одновременный join двух претендентов на десятый слот принимает одного. Два одновременных create/join одного user в разных кабинетах дают только одно active Membership; проверка настоящих SQL-транзакций.
**AC-04.** Выход creator сохраняет остальных/банк; выход обычного участника сохраняет журнал; после выхода нет доступа, включая старый widget token. Последний выход предупреждает и архивирует. Новый кабинет не наследует старые pending.
**AC-05.** QR/код одно приглашение, expire24h, revoke/used не принимаются, scan/preview не consumes. Wrong environment/format не открывают произвольную ссылку.
**AC-06.** Показ/отправка QR и копирование кода. Яркость восстановлена при закрытии/фоне/share sheet. Камера с отказом оставляет ручной вход, один кадр не создаёт несколько join.

## Деньги и настройки

**AC-07.** Создать спринт 1–366 дней с включённой конечной датой; второй активный отклонён. Полночь во время сохранения не создаёт неверную дату старта.
**AC-08.** 10 000/10 дней, расход600; завтра carry400, bank9400, варианты1400/1044,44. Расход снижает A на полную сумму.
**AC-09.** Первый choose_carry общий для всех, второй не перезаписывает; stale preview/смена суток требуют нового подтверждения.
**AC-10.** Пополнения агрегируются до floor. Последний день A=B; отрицательные значения; 100/3→33,33+33,33+33,34; C не создаёт банк.
**AC-11.** 10 000−1 200, target9 000: original=10 000, Entries неизменны, delta=+200, bank9 000. No-op и повтор команды не создают новую корректировку.
**AC-12.** Пример 9 000/9, расход600: bank8400/today400; изменить bank10200→today600; только N6→today900; оба→today1200. Два поля сохраняются атомарно.
**AC-13.** Новая дата действует с текущего дня; исходный вчерашний carry не пересчитывается с новым сроком. Нельзя поставить вчера/переоткрыть завершённый. Можно поставить сегодня.
**AC-14.** Покупка/другая правка во время edit sprint вызывает conflict с сохранением черновика; не теряется покупка, не происходит silent overwrite target. Проверка expected_business_date после полуночи.
**AC-15.** Поздняя покупка после корректировки уменьшает bank; delta не переоценивается от target. Поздняя вчерашняя покупка уточняет carry при сохранённом mode. Сервисное изменение не учитывается одновременно как Entries и SprintRevisions.
**AC-16.** Несколько правок одного дня, продление/сокращение, отрицательная корректировка, день без открытия, последняя дата и as-of до изменения покрыты эталоном/сервером/Swift.
**AC-17.** Два участника исправляют одну запись — одна версия принимается, другой получает новую без потери ввода. Удаление с expected version возвращает правильный эффект, аудит сохраняется.

## Сеть и данные

**AC-18.** Два и более одновременных независимых расхода сохраняются все. Не «последний баланс победил».
**AC-19.** Повтор одной команды20 раз создаёт ровно одну запись/revision. Тот же id с другим payload отклоняется. Потерянный ответ после commit не вызывает двойной локальный учёт.
**AC-20.** Offline user пишет, остальные online пишут; после reconnect единое состояние. Kill/reboot/обновление TestFlight не теряют pending. Проблема диска не очищает ввод.
**AC-21.** /sync согласовывает receipts и snapshot; поздний ответ меньшей revision или вчерашней даты не откатывает состояние; новая покупка во время sync не теряется.
**AC-22.** Запись прошлого завершённого спринта после подтверждения меняет только его. Ошибка часов/даты требует ясного восстановления, без молчаливого переноса в current sprint.
**AC-23.** SQL schema/migrations на чистой БД и повторном deploy; FK/unique/lock order/rollback, gross exposure, capacity; race tests не заменены in-memory fake.

## Клиент, виджет, эксплуатация

**AC-24.** Реальные два iPhone: основной экран, мгновенный ввод, запятая, знак, длинные числа, VoiceOver, Dynamic Type, история/архив. Нет категорий и лишних экранов покупки.
**AC-25.** TestFlight medium widget устанавливается, открывает ввод, честно показывает stale/no access/completed/pending. Испытать Low Power, force quit, locked-after-reboot, сеть off, midnight. Секундный widget SLA не заявляется.
**AC-26.** Apple/Keychain/APNs/Widget tokens имеют нужные audience/scope/environment, отзыв действует, чужой ID не раскрывает данные. QR/токены/финансовые payload отсутствуют в логах.
**AC-27.** Staging и production сосуществуют; разные базы, локальные данные, shared groups/keys/bundle, приглашения и виджеты. Нельзя снести staging скриптом production release.
**AC-28.** Production доступен на реальных сетях пользователей без VPN; зафиксировать условия и задержку, не объявлять гарантию всей территории Китая.
**AC-29.** Обновление сборки поверх прежней сохраняет сессию/историю/outbox, миграции локальной базы тестируются. Выпуск следующего TestFlight воспроизводим из репозитория.
**AC-30.** Backup восстановлен на отдельной среде; совпадают bank/history/receipts/revisions, выполняется согласованный deletion replay. Проверены инструкции/доступ owner/секреты и мониторинг.
**AC-31.** R-01 закрыт: полное удаление аккаунта реализовано согласно согласованной политике и реальной проверке данных/Apple revoke, не смешивается с leave/logout.
**AC-32.** Протокол сдачи подписан/принят, все critical дефекты закрыты, источники/сервер/релизы принадлежат заказчику, ответственный за срок TestFlight и поддержку определён.

## Нефункциональные цели

Локальный save+display p95≤150мс на более слабом целевом устройстве. Изменение на втором открытом клиенте p95≤5с при сети RTT≤500мс. API p95≤300мс на согласованной инфраструктуре (не включая внешнюю сеть). Это целевые метрики, здесь не измеренные. Widget best effort без секундного SLA.
