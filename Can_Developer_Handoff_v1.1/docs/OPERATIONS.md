# 07. Эксплуатация и выпуск

## Постоянные среды

Staging сохраняется после сдачи. Production — настоящий бюджет. Отдельные базы, секреты, ключи, API hosts, Bundle ID, App Group, Keychain groups, deep-link scheme, иконка/название сборки. «Can Staging» заметно отличается от Can. В пользовательском приложении нет переключателя API. QR имеет environment, чужая среда отклоняется. Реальные операции не копируются в staging без отдельного основания/обезличивания.

TestFlight — способ доставки, не название среды backend. Проверять APNs entitlement фактической сборки; staging-версия из TestFlight не обязательно использует sandbox APNs.

## Владелец ресурсов

Репозиторий, Apple Account Holder, домен, хостинг и биллинг под контролем заказчика. Не выпускать в личной Apple-команде подрядчика с обещанием переноса. Подрядчик работает отдельными ролями/учётками; секреты через безопасное хранилище, не чат/Git. При передаче — инвентаризация и ротация выданных доступов.

Apple: организация может делегировать участникам команды соответствующие права. В Individual-членстве приглашённый App Store Connect пользователь не становится членом Apple Developer team и не получает автоматически Certificates, Identifiers & Profiles [S-01]. В M0 зафиксировать рабочий путь подписи: действия владельца по сертификатам/идентификаторам, согласованное signing-окружение под его контролем и безопасная процедура выпуска. Не просить основной пароль/2FA код как постоянный «доступ».

## Сервер

Небольшой API + worker + PostgreSQL. Сервер недоступен напрямую к БД из интернета. HTTPS, миграции, health/live, health/ready, ограничение доступа админа, регулярные security updates. Регион/поставщик ещё не выбраны. Цель — проверить реальные мобильную и Wi-Fi сети двух пользователей в Китае без VPN; регион «близко к Шанхаю» не доказательство качества связи.

CI: lint/test, reference fixtures, миграции на чистой БД, backend integration, Swift tests/Xcode build на macOS, проверка секретов. Production deploy только после staging smoke и проверенного rollback/forward-fix. Downgrade БД не должен удалять новые финансовые события; перед потенциально необратимой миграцией backup и явное одобрение.

## Backup/monitoring

Предлагаемая цель: ежедневный зашифрованный backup вне основного сервера, хранение 30 дней, RPO≤24ч и целевой RTO≤4ч после доступа к инфраструктуре. Это требования для испытания, не достигнутые показатели. При более строгом RPO потребуются более частые backup/PITR, согласовать стоимость до запуска. Восстановление реально выполнить на изолированной базе; verify counts, projection, receipts и deletion replay.

Мониторинг: доступность API/DB, p95 latency/ошибки, диск, возраст последнего успешного backup, очередь push и истечение сертификатов/доменов/членства/TestFlight. Не собирать финансовые payload в логи. Owner получает способ узнать об отказе и runbook.

## TestFlight

Две целевые физические установки; приложение и Widget Extension, Apple login, App Group, подпись, processing build, группы тестировщиков. Для внешнего тестирования первый build направляется на beta review; обычного участника бюджета не надо ради этого делать администратором App Store Connect [S-02]. Установка приложения через TestFlight и приглашение в общий бюджет — два разных шага.

Сборка доступна до 90 дней [S-02, S-03]. Планировать выпуск с запасом, например примерно раз в 60 дней; точный ответственный и cadence фиксируются при сдаче. Новая сборка не должна уничтожать local outbox. Поддержка TestFlight не прекращается сама после первой установки.

## Что сдаётся

Исходники и история Git; Xcode-проект и версии SDK/зависимостей; backend/миграции/конфиги; управление staging/production; инструкции build/deploy/rollback/backup/restore/new TestFlight; опубликованный тестовый build на owner team; акт приёмки с evidence; список известных ограничений; список аккаунтов/ключей без самих секретов. Отдельно договориться о периоде исправления дефектов и ongoing maintenance; стоимость в пакете не установлена.
