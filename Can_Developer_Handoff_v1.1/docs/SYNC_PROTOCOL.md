# 05. Офлайн, синхронизация и виджет

## 6.1. Надёжная локальная запись

Нажатие подтверждения создаёт Entry draft и PendingCommand одной транзакцией локальной базы. Только после успешного сохранения UI очищает сумму и сообщает «сохранено». Если диск недоступен, введённое значение остаётся. Отсутствие интернета не блокирует эту операцию.

Состояния очереди: queued, sending, acknowledged, included, needs_attention. После перезапуска sending не означает неуспех: клиент сначала сверяет receipt либо повторяет неизменную команду. acknowledged означает ответ сервера, included — подтверждённое включение в полученный snapshot. При ограничении 1000 ожидающих записей новый ввод сохраняется черновиком и показывается понятная ошибка; ранее записанное не удаляется.

До первой передачи можно отредактировать/удалить queued. После возможной отправки тело команды неизменно. Для отмены такой покупки сначала выясняется результат, затем при необходимости отправляется void. Нельзя локально забыть запись, которая могла уже попасть партнёру.

## 6.2. Защита от двойного локального учёта

Самая опасная последовательность: сервер принял расход, ответ потерялся, приложение скачало новый баланс и дополнительно вычло свою «неотправленную» покупку. Получится двойное списание только на экране.

Поэтому `/sync` получает до 1000 unresolved command_id и возвращает в одном согласованном чтении snapshot и статусы всех этих команд: applied, rejected, unknown. Snapshot и receipts формируются под одной короткой блокировкой кабинета либо эквивалентной согласованной транзакцией. Клиент применяет ответ атомарно.

К подтверждённым дневным агрегатам локально добавляются только unknown-команды add_entry соответствующего спринта. applied уже включены; rejected не накладываются и требуют действий. Записи прежнего спринта никогда не накладываются на текущий. Неизвестный receipt сам по себе не доказывает отсутствие entry: повторная отправка UUID обязана проверить и существующую запись.

Ответ меньшей revision не заменяет больший. При той же revision учитывается business_date: вчерашний ответ не возвращает вчерашнее число под «Сегодня». После применения подтверждённой версии повторяется чистый BudgetEngine над серверными агрегатами и ещё неучтёнными локальными добавлениями.

## 6.3. Повторные запросы

Повтор сети: exponential backoff с jitter, ориентир 1, 2, 4, 8, 16, максимум 60 секунд. Возвращение сети/foreground позволяет попытку сразу. При недоступной авторизации сохраняются outbox и черновик; выйти из аккаунта с очередью можно только после предупреждения и явного выбора. Для другого пользователя чужая очередь не показывается и не отправляется.

Серверный timeout после commit не порождает новый UUID. Сетевое сообщение не должно утверждать «расход не записан», пока receipt неизвестен: текст «Сохранено на телефоне; проверяем синхронизацию».

## 6.4. Время устройства и завершённые спринты

Клиент хранит последнее смещение относительно server_time как ориентир. Сервер переводит occurred_at в пояс кабинета. Будущее время дальше 5 минут от серверного или дата вне действовавших на неё границ спринта приводит к needs_attention. Время реальной покупки нельзя криптографически доказать; значение фиксирует пользовательский ввод.

После окончания запись не переносится в новый спринт автоматически. Просроченная доставка требует явного подтверждения добавления в архив; отчёт уточняется, срок не продлевается. Исправление ошибочной даты устройства допускается только в этом сценарии восстановления с явным сообщением и аудитом; обычный ручной выбор прошлой даты не нужен в v1.

Офлайн-расход прошлого дня может изменить уже выбранный carry. Сохраняется способ, не показанная ранее сумма. Сообщение о перерасчёте не требует второго подтверждения того же режима.

## 6.5. WidgetKit

Обязателен Home Screen systemMedium: «Сегодня», крупное число, небольшой статус свежести; нажатие открывает ввод. Не нужен отдельный Telegram-клиент. Widget extension поставляется внутри iOS-приложения; интерактивность ограничивается открытием приложения в первой версии.

Системное расписание и бюджет обновлений не позволяют обещать постоянную работу или обновление каждую секунду [S-04]. Новые версии WidgetKit поддерживают push-обновления виджетов; использовать их при наличии соответствующего API и проверенной OS availability. Это не снимает системных ограничений и не делает виджет realtime-подпиской [S-05].

Основные каналы: reload после собственной записи; fetch timeline при запуске extension; локальная timeline-запись на следующую полночь; app background push как best effort; WidgetKit push на поддерживаемых ОС. Background push может откладываться или не доставляться — его нельзя считать гарантией [S-06].

Сервер получает app APNs token и widget push token как разные данные. Реализацию payload/topic/entitlements брать из документации актуального SDK, не подставлять app token вместо widget token. Worker повторяет временные ошибки, удаляет invalid tokens, объединяет устаревшие запросы обновления; push не содержит сумм, имён или истории.

## 6.6. Shared container и права

App Group snapshot записывается приложением атомарно через временный файл и rename. Поля: версия формата, revision, business_date, calculated_at, last_successful_sync_at, today_minor, bank_minor, pending_count, carry_pending, sprint status. Extension не пишет в SwiftData приложения и не меняет финансовую очередь.

При сетевом fetch extension хранит отдельный cache. Нельзя заменить локальную проекцию с pending_count > 0 серверным числом без учёта ожидающих операций: в таком случае показывается проекция приложения с отметкой «Есть несинхронизированные траты» до его sync. Если основной клиент не имеет pending, можно показать более свежий серверный snapshot.

Widget Bearer разрешает только минимальный snapshot одного кабинета. Срок 7 дней, обновление при открытии приложения при остатке <1 дня. Токен находится в Keychain Access Group, не в UserDefaults/App Group JSON [S-07]. Истёкший/отозванный доступ показывает «Откройте приложение», без цикла логина в extension.

## 6.7. Визуальные состояния

Актуальные данные: число и при необходимости время. Данные старше 15 минут: «Обновлено … назад», порог проектный, не обещание частоты. Полночь без свежего ответа: «Новый день — откройте приложение» или корректная локальная предварительная проекция с явной пометкой; старое значение не выдаётся за сегодняшний подтверждённый лимит.

Нет кабинета/спринта — предложение открыть приложение. Спринт завершён — «Спринт завершён». Ошибка сети — последний подтверждённый snapshot с временем, а не ноль. Заблокированное после перезапуска устройство может не дать Keychain-доступ; нейтральное состояние вместо аварии. Force-quit, Low Power Mode и длительное неоткрытие приложения входят в реальные тесты.

## Дополнения v1.1

Snapshot содержит SprintRevisions; их фиксированные delta применяются ровно один раз. При неизвестной calculation_version не считать старым движком. Перед настройкой остатка отправить собственный outbox, получить согласованный snapshot и сохранить basis revision/business_date. Без сети update_sprint не становится отложенной target-командой: она опасно зависела бы от уже изменившегося банка.

Очередь и Keychain изолированы по environment/user/membership. При выходе на другом устройстве отозванный доступ блокирует отправку; уже подтверждённые записи не исчезают. После повторного вступления прежние unresolved команды сначала сверяются, а не переносятся в новый Membership автоматически.

Сигнал push расходится всем активным устройствам до десяти участников, не только паре телефонов. Уровень среды API не равен APNs environment: TestFlight-сборка staging может использовать production APNs; выбирать endpoint APNs по entitlement подписанной сборки, а не по имени среды. App/Widget tokens разные.

Пересчитывать клиентскую базу с revisions и pending в одной сериализованной локальной транзакции. Если во время /sync добавили ещё одну покупку, её не потерять: применять ответ к снимку запрошенных unresolved id, а новые id оставить в очереди. `unknown` не означает «отклонено»: сервер мог принять команду после консистентного чтения. Повтор с тем же id разрешает этот случай.

Проектные лимиты/пороги (1000 pending, 3 секунды foreground polling, 15 минут stale, 5 минут clock-skew) фиксируются конфигурацией и тестируются; это не свойства iOS и не обещание доступности сети. Ссылки S-* раскрыты в SOURCES.md.
