# Can / «Можно» — iPhone и виджет

Нативный SwiftUI проект для iPhone с iOS 17+, один production API, вход только через Apple. Откройте `Can.xcodeproj`, выберите общую схему `Can`. XcodeGen, CocoaPods и сторонние Swift-пакеты не требуются. Для текущей загрузки в App Store Connect нужен Xcode 26+ с iOS 26 SDK; минимальная версия ОС приложения остаётся 17.0. В CI выбран Xcode 26.3.

## Публичная конфигурация владельца

Заполните `Config/Owner.xcconfig` своими **несекретными** значениями:

| Ключ | Значение |
|---|---|
| `CAN_DEVELOPMENT_TEAM` | Team ID Apple Developer владельца |
| `CAN_BUNDLE_ID` | Зарегистрированный App ID основного приложения |
| `CAN_WIDGET_BUNDLE_ID` | Отдельный App ID расширения, обычно `<app bundle>.widget` |
| `CAN_APP_GROUP` | Зарегистрированный `group.…`, одинаковый для обоих targets |
| `CAN_KEYCHAIN_GROUP` | Общая группа Keychain без Team/App Identifier Prefix; prefix добавляет Xcode |
| `CAN_API_BASE_URL` | HTTPS origin production API без `/v1`; выбран `https:/$()/151.243.217.6` |

`/$()/` в xcconfig предотвращает трактовку `//` как комментария; в Info.plist получается обычный `https://`. Адрес `.invalid` намеренно блокирует вход и сетевые операции. Токены, `.p8`, пароли и сертификаты в репозиторий не добавляются.

Владелец выбрал работу по публичному IP без домена. Оба Info.plist содержат точную запись `151.243.217.6` в `NSExceptionDomains`: insecure HTTP запрещён, минимальная TLS 1.2 и Forward Secrecy сохранены. Глобальное отключение ATS и собственная проверка доверия не добавляются. Сервер должен предъявлять публично доверенный сертификат с этим IP в SAN; установка корневого сертификата на телефоны не требуется. Статика проверяет соответствие origin и ATS обеих целей; работу URLSession на целевых iPhone ещё необходимо проверить. При смене IP одновременно обновите `Owner.xcconfig` и обе ATS-записи и выпустите новую сборку. [Apple: IP-подключения с iOS 17](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowslocalnetworking).

В Apple Developer включите Sign in with Apple для основного App ID, App Groups и Push Notifications для соответствующих App IDs, разрешите общую группу Keychain в профилях. Оба target должны подписываться командой владельца. У каждого target первая Keychain group приватная (`AppIdentifierPrefix + bundle ID`); общая группа используется **явно** только для read-only токена/регистрации виджета. Access/refresh tokens приложения в общую группу не записываются.

В backend `CAN_APPLE_CLIENT_ID` должен совпадать с bundle ID приложения, Team/Key ID и Apple private key настраиваются владельцем в защищённом серверном хранилище. Это нативный Apple login: challenge → SHA-256 nonce → identity token + authorization code → backend. Отдельный web Service ID, redirect URL или associated domain этому потоку не нужны. HTTPS адрес сервера задаётся `CAN_API_BASE_URL`. Вход и отзыв Apple обязательно проверить настоящим подписанным приложением.

Debug использует entitlement `aps-environment=development`, а backend-регистрацию `apns_environment=sandbox`. Release использует `production` в обоих местах. App APNs topic — bundle ID приложения. Для прямого WidgetKit push на iOS 26+ требуется отдельно проверить topic/capability расширения в аккаунте владельца и APNs. iOS 17–25 используют обычное обновление приложения, общий снимок и WidgetKit timeline; система не гарантирует точное время фонового обновления.

## Проверки

Из корня репозитория:

```sh
make ios-build
make ios-test
python3 apps/ios/tools/check_project.py
```

Первые две команды требуют Mac/Xcode; `ios-test` выбирает доступный iPhone Simulator с iOS 17+ (при необходимости передайте `IOS_DESTINATION`). Simulator-сборка выполняется без подписи. XCTest target содержит 25 методов: все 240 исходных эталонов calculation_version=2, целые копейки, отрицательное округление, временные границы, reconciliation потерянных ответов, конкурентный ввод, изоляция эпох членства, противоречивые receipts, recovery с неизменным entry ID, восстановление durable state, nullable аудит, безопасный разбор QR и сохранение очереди при восстановлении сервера; дополнительно — immutable deletion replay, смена reauth proof без потери прежнего, возобновляемая очистка, изоляция файлов двух аккаунтов и отсутствие выдуманного имени в истории.

`check_project.py` проверяет синтаксическую структуру project.pbxproj, ссылки и membership targets, shared test scheme, plist/entitlements, отделение private/shared Keychain, APNs среды, наличие PNG 1024×1024 и неизменность эталонного Swift-расчёта/fixtures. Это **не** компиляция Swift и **не** выполнение XCTest. Во время реализации в Linux прошла только эта статическая проверка; Xcode build, XCTest, подпись, Apple login, APNs и проверки на устройствах здесь не выполнялись.

После добавления или удаления Swift-файлов обновите проверяемый проект стандартным Python:

```sh
python3 apps/ios/tools/generate_project.py
python3 apps/ios/tools/check_project.py
```

Генератор необязателен для сборки существующего проекта. `tools/generate_icon.py` воспроизводит собственный простой знак Can без внешних изображений и шрифтов.

## Поведение и хранение

- `Shared/BudgetEngine.swift` — неизменённый Swift reference v2. Суммы хранятся в `Int64` копейках; бизнес-даты — `Asia/Shanghai`.
- `LocalState.swift` хранит снимок, ввод, покупки и pending commands одним атомарно заменяемым защищённым JSON-файлом **для конкретного user ID** в отдельной его директории Application Support. При обновлении прежний плоский файл переносится в эту директорию без изменения содержимого; при удалении стираются и остатки незавершённых атомарных записей, и legacy файл этого же пользователя. Файл исключён из backup. Здесь используется одна сериализуемая транзакция вместо двух независимых хранилищ Entry/Outbox; запись подтверждается интерфейсом только после успешной записи на диск. Финансовые данные не лежат в UserDefaults. Нужны реальные force-quit/locked-device проверки на iPhone.
- Все изменяющие бюджет команды сохраняются с неизменным command ID и payload перед отправкой. Неизвестный сетевой исход сохраняется. `/sync` атомарно сверяет полный набор receipts со снимком и сохраняет покупки, введённые во время запроса. Квитанция проверяется на внутреннюю согласованность до удаления очереди.
- Команды прежнего членства остаются в отдельном состоянии и не меняют баланс/доступность действий нового кабинета. Read-only `/v1/commands/{id}/receipt` проверяет старый исход без повторного исполнения онлайн-команды. Отправленную запись с неизвестным исходом интерфейс не удаляет.
- Исправление часов и подтверждение поздней записи создают новый command ID, сохраняют исходный entry ID и ссылку на terminal rejection; исходный sprint/membership не меняются.
- AppGroup содержит только краткий widget snapshot. Расширение получает отдельный read-only bearer; сессия приложения ему недоступна. После выхода, подтверждённой смены членства, отзыва Apple или окончательного 401 общий токен/снимок очищаются. При сети после ожидания перечитывается актуальное локальное состояние, чтобы не затереть предварительный баланс или выйти за границы аккаунта.
- Виджет `.systemMedium` показывает дату, предварительность/давность и переход `can://expense`. После полуночи старое число скрывается. Timeline включает отметку устаревания через 15 минут и нейтральную запись следующего дня. На iOS 26+ отдельная Widget конфигурация принимает WidgetKit push token; приложение регистрирует его при следующем открытии.
- R01 принят: при удалении аккаунта общий журнал сохраняет операции, суммы и даты; имя и связь с аккаунтом стираются. Неизвестный автор отображается как «Без имени». Выход из кабинета и logout остаются отдельными действиями.

## Удаление аккаунта и потерянный ответ

В настройках есть объяснение последствий, отдельное подтверждение Apple и destructive confirmation. Интерфейс показывает число ожидающих записей/действий: после принятия удаления их локальные черновики тоже стираются; пользователь может сначала открыть синхронизацию. Удаление не блокируется навсегда из-за неразрешимой старой очереди.

До `DELETE /v1/me` в **приватном Keychain** атомарно сохраняются immutable command ID, `confirm_shared_history_changes=true`, идентификатор локального владельца и исходный reauth proof. HTTP 202 должен содержать валидные `job_id`, `status=accepted`, `primary_deletion_deadline` и `backup_retention_days=30`. Это принятие запроса, не завершение серверного/Apple/backup удаления; экран явно показывает разницу и срок.

После таймаута или перезапуска сначала повторяется тот же DELETE с исходным `X-Reauth-Token` без bearer-сессии. Backend может подтвердить квитанцию после отзыва сессий и физического удаления пользователя. 401 не считается успехом и не разрешает очистку. Если запрос действительно не принят и нужно новое подтверждение Apple, клиент проверяет исходные proofs ещё раз, сохраняет свежий proof **с тем же command ID/body** перед отправкой и удерживает предыдущие proofs до ответа. Это защищает от принятия первого запроса между проверкой и повтором.

После 202 сначала записывается защищённый marker принятия, затем удаляются только файл состояния этого user ID (включая очередь), его device ID, identity mapping, соответствующая сессия, Apple ID и widget/cache credentials. Ошибка защищённого хранилища оставляет marker для следующего запуска; бюджет и обычные действия в этом состоянии скрыты. После успешной локальной очистки удаляются marker и все сохранённые reauth proofs. Чужие per-user файлы и чужая активная сессия сохраняются. Общий widget cache очищается только при отсутствии другой активной локальной сессии.

На другом устройстве обычный 401 скрывает widget/отзывает локальную сессию, но не доказывает удаление аккаунта. Очистка его личного файла разрешается после свежего Apple login, когда сервер вернул `account_deletion_pending` после проверки Apple identity, а локальная защищённая привязка Apple → user ID совпала. Офлайн-устройство нельзя очистить удалённо без его следующего подключения и такого подтверждения. Успешный новый вход после окончательного удаления создаёт новый пустой аккаунт с новым user ID. Если второе устройство пропустило состояние `account_deletion_pending` и увидело уже новый UUID, одного отличия UUID недостаточно для автоматического стирания старой очереди (оно возможно и после восстановления БД). Клиент сохраняет защищённую привязку прежних локальных наборов к тому же Apple Account. В «Настройки → Прежние данные на этом iPhone» показано количество ожидающих записей/действий. После свежего подтверждения того же Apple Account пользователь может явно удалить выбранный прежний набор только на этом телефоне; текущие session, Apple identity key, очередь и widget сохраняются. По умолчанию прежние данные остаются скрытыми и не исполняются от нового аккаунта.

Если при неизвестном исходе удаления свежий вход тем же Apple Account уже вернул новый UUID, приложение сохраняет новую сессию и не отправляет DELETE для неё. Экран предлагает сохранить прежние данные и продолжить либо явно удалить их локально. В первом случае исходный proof остаётся в защищённом карантине: в настройках его можно проверить анонимным replay исходной квитанции. При 202 очищаются только старые данные; при 401 они сохраняются. Локальная очистка имеет отдельное предупреждение и не называется удалением аккаунта на сервере.

Обязательные проверки на Mac/двух iPhone: потеря ответа 202, завершение процесса до/после marker, заблокированный Keychain, повтор со старым proof после истечения сессии, reauth другим Apple Account, отсутствие ложного успеха при 401, сохранность другого аккаунта на том же телефоне, удаление с другого телефона, анонимные авторы в текущей истории/аудите/архиве. XCTest и эти сценарии в Linux не выполнялись.

## Следующий выпуск и восстановление

1. Выполните проверки на Mac, затем подпишите оба targets командой владельца. На двух целевых iPhone проверьте Apple sign-in, общий кабинет/приглашение, офлайн + force quit, потерянный ответ, одновременный перенос/правки, уход/повторное вступление, старый спринт, смену дня и виджет. Внесите реальные результаты в общий acceptance record.
2. Увеличьте `CURRENT_PROJECT_VERSION`, при необходимости `MARKETING_VERSION`. В Xcode выберите `Any iOS Device (arm64)` → Product → Archive → Validate → Distribute App → App Store Connect. Сертификаты/профили и upload-доступ должны принадлежать владельцу. Приложение и extension используют одну версию/build number.
3. Дождитесь обработки в App Store Connect и назначьте сборку двум тестировщикам. Внешним тестировщикам может потребоваться Beta App Review. TestFlight-сборка действует 90 дней; следующую загрузку планирует владелец/оператор. Наличие кода не подтверждает доступ к Apple аккаунту или выполненную загрузку.
4. После восстановления backend из backup приложение обычно принимает только неубывающие revision и бизнес-даты. Если сервер восстановлен на более раннюю revision, откройте «Настройки → Синхронизация → Обновить бюджет после восстановления сервера» и подтвердите действие. Очищается только подтверждённый локальный снимок; очередь/неизвестные результаты и их ID сохраняются. Если ранее принятая запись после восстановления имеет отсутствующую квитанцию, она требует отдельного подтверждения повтора прежнего идентификатора и данных; автоматического повтора такого случая нет. Проверьте receipts и общие суммы на обоих телефонах; не создавайте дубли покупок вручную. Потерянные сервером операции за пределами backup RPO не восстанавливаются автоматически из уже очищенной клиентской очереди.
5. При смене API-домена выпускается сборка с новым публичным адресом. Не меняйте AppGroup/Keychain group/bundle IDs существующей установки без отдельного плана миграции: это может лишить новую сборку доступа к прежним защищённым данным.

Фактическая приёмка TestFlight/сервера/виджета ещё требует работающего production backend, владельческих Apple capabilities и двух телефонов. Реализованный исходный код не заменяет эти проверки.
